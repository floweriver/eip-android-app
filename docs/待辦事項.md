### P1 — 使用者回報的問題

**T-02 雙筆並存時切換邏輯不正確** *(使用者項目 1)*
- Symptom: when two pencils appear in the pairing list, the app does not pick
  the right one to switch to.
- Suspect area: `BluetoothViewModel.switchTo()` / `startAutoConnectLoop()` /
  `preferredDeviceId`.
- Auto-connect picks `candidates.firstOrNull { it.id == preferredDeviceId }
  ?: candidates.firstOrNull()` — plain list order, no RSSI ranking, and
  `isNearby` is set to `true` for every bonded device regardless of proximity.
- Needs clarification: what is "好的那隻"? Strongest signal / last used /
  actually in range?
- ⚠️ Only one GATT connection at a time on these pencils. Switching = disconnect
  A → connect B.

**T-03 排版：小視窗下標籤重疊** *(使用者項目 2)*
- Symptom: on Chromebook with a shrunk window, Signal Strength label overlaps
  the shortcut labels.
- Root cause identified: `StylusVerticalView` (DebugScreen.kt:262) positions
  four anchors by absolute offset from centre, using **two incompatible
  coordinate systems**:
  - `topIndicatorCenterY` = `-screenH * 0.35f` → scales
  - `midTopIndicatorCenterY` = `35.dp + …` → **fixed**
  - `midBottomIndicatorCenterY` = `105.dp + …` → **fixed**
  - `bottomIndicatorCenterY` = `screenH * 0.30f` → scales
- The pencil artwork scales with height (`requiredWidth(screenH * 0.92f)` then
  `rotate(-90f)`, so on-screen pencil length = `0.92 * screenH`). Two anchors
  track it, two do not. Shrink the window → they collide.
- Proposed fix (方案 A): express all four as `(f - 0.5f) * 0.92f * screenH`,
  where `f` = fractional position along the pencil. Requires reading actual
  button positions off the artwork; needs on-device tuning.
- Secondary issue: `isLandscape` comes from `configuration.orientation`, an
  unreliable signal on ChromeOS free-form windows. `BoxWithConstraints` already
  exposes `maxWidth`/`maxHeight` — use those.
- Blocked on: user confirmation of which pair actually overlaps + a screenshot.

**T-04 舊款 Lenovo Duet 當機** *(使用者項目 3)*
- Symptoms (as reported): app crashes easily on open; all shortcuts appear on
  open; pressing Factory Reset crashes it.
- Open question from user: our bug, or is the device just too weak?
- Needs clarification: "打開時跑出所有快捷鍵" — all labels render overlapping
  (i.e. same root cause as T-03), or the mapping panel auto-opens?
- Hypothesis to test: memory. Original Duet (2020) is low-end / 4 GB. Play's own
  R8 recommendation (T-05) is framed as a memory-efficiency issue — the two may
  be connected.
- `factoryReset()` (BluetoothViewModel.kt:298) fires the command, calls
  `resetState()`, then immediately `queryInitialStatus()` — which sleeps 1.5 s
  then bursts 8 writes. Worth checking whether the device is mid-reset/
  disconnecting while that burst runs.
- No confirmation dialog on the Reset button (DebugScreen.kt:436) — destructive
  action, one tap.
- Next step: capture a logcat from the Duet during the crash. Guessing without
  a stack trace is not worth it.
- ⚠️ Note the overlap with T-07: "按 Factory Reset 就當機" (T-04) and "按
  Factory Reset 沒反應" (T-07) may share the same upstream cause.

**T-07 部分裝置讀不到快捷鍵，全部顯示 No Function** *(使用者項目 4)*
- Symptom: on some devices, after connecting, every button shows "No Function" —
  but the shortcuts genuinely still work on the pencil. So the pencil is fine;
  the app failed to *read* the mapping and then displayed that failure as if it
  were a real answer.
- **Display defect** (`ActionGroupLabel`, DebugScreen.kt:319):
  `settings[keyCode] ?: Function.NONE` → a missing entry is indistinguishable
  from a genuine "no function". There is no loading / unknown state.
- **Why the read fails** (`queryInitialStatus()`, BluetoothViewModel.kt:256):
  fires 8 writes spaced 20 ms apart, all `WRITE_TYPE_NO_RESPONSE`. No-response
  writes have no flow control; when the stack's buffer is full they are dropped
  silently. Slow/older BLE stacks (Duet, ChromeOS) are the ones that miss them.
- **No retry.** Nothing re-queries a key whose response never arrived. State
  stays empty for the rest of the session.
- **Failures are invisible** — see 已知地雷: sent packets are never logged and
  write results are never checked. Currently there is no way to tell "query was
  never sent", "was sent but dropped", or "was answered and mis-parsed" apart.
- Also suspect: `toggleNotifications()` CCCD descriptor write is async and is
  not awaited before the query burst. The fixed `delay(1500)` usually covers it,
  but nothing guarantees it.
- ⚠️ `setPencilFunctionWithRetry()` (BluetoothViewModel.kt:269) **does not
  retry** despite the name. It fires once, optimistically updates local state,
  and never verifies. Same class of bug in the write direction — worth fixing
  together.

**T-07 追加事證 (2026-08-31)：故障態下按 Factory Reset 也沒反應**

This widens the fault from "reads fail" to "the whole write path is dead", and
points at a single upstream cause rather than dropped no-response writes.

- `onServicesDiscovered()` (BluetoothViewModel.kt:184) sets state to **READY
  before verifying the service or characteristic actually exist**:
  ```
  connectTimeoutJob?.cancel()
  updateDeviceConnectionState(addr, READY)   // ← declared READY unconditionally
  toggleNotifications(SERVICE_UUID, NOTIFY_CHAR_UUID, true)
  queryInitialStatus()
  ```
- If `getService(ffe0)` returns null (stale GATT attribute cache — common on
  ChromeOS / older stacks after re-pairing), then:
  - `toggleNotifications()` hits `?: return` (line 330) → CCCD never written →
    **no notifications ever arrive** → all keys stay unset → all "No Function"
  - every `sendCommand()` hits `?: return` (line 319) → **every command is a
    silent no-op**, including Factory Reset
  - the UI still shows READY / green dot / main screen
- That single failure reproduces every reported symptom at once, including the
  pencil itself continuing to work normally.

⚠️ **Two readings to distinguish before fixing — they need opposite fixes:**

| | 讀法 A | 讀法 B |
|---|---|---|
| 失效點 | `getService()` returns null | service OK, CCCD write failed (line 333 `descriptor?.let`) |
| 寫入方向 | dead | **works** |
| 按下 Reset | nothing happens | **pencil IS actually reset**, UI just shows nothing |

Reading B is the dangerous one: Factory Reset would be silently wiping the
user's mappings with zero feedback. `factoryReset()` also calls `resetState()`
then re-queries, so the UI looks unchanged either way — the readings are
indistinguishable from the screen.

**Test to tell them apart:** in the broken state, press Factory Reset, then
check on the pencil itself whether the button mappings actually changed.

- Root pattern: **every failure path in this file is a silent `?: return`** —
  lines 318, 319, 330, 333, 396, plus `switchTo()`. Nothing logs, nothing
  surfaces to the UI. Combined with sent packets never being logged
  (see 已知地雷), a fully dead command path is indistinguishable from a
  healthy one.
- Revised fix direction (supersedes the flow-control theory as the primary):
  1. verify service + write/notify characteristics exist before declaring READY;
     fail loudly and retry/reconnect if not
  2. log the send direction and check write results
  3. distinguish unknown from NONE in the UI
  4. flow control / retry for the query burst — still worth doing, but likely
     secondary

So: **service discovery reported success, READY was set, yet nothing goes out

✅ **讀法 B 排除.** Setting a shortcut has no effect on the pencil → the write

✅ **讀法 A 確立**: `getService(ffe0)` — or the ffe2/ffe3 characteristic lookup —

⚠️ **Diagnostic blind spot:** `onServicesDiscovered()` has **no logging at all**

**零改動的驗證（先做這些，不需要動 code）**
1. **nRF Connect** (or any generic BLE scanner) on the failing device → connect
   to the pencil → does service `ffe0` with `ffe2`/`ffe3` appear?
   - not visible → the platform/pencil is not exposing it; our lookup is fine
   - visible → the service is there and our code's lookup or timing is at fault
2. **Unpair and re-pair** the pencil on the failing device. If the fault clears,
   it is the Android **stale GATT attribute cache** — the classic cause of
   "connects fine, services empty". Remedy is `gatt.refresh()` (hidden API) or
   forcing re-discovery.
3. Does force-quitting and reopening the app clear it, or does it persist across
   launches? Distinguishes a per-session race from a cached-state problem.

**需核准的診斷用修改（尚未進行）**
- log the resolved service/characteristic UUIDs in `onServicesDiscovered()`
- log the send direction and the `writeCharacteristic` return value

**T-07 事證五 (2026-08-31)：裝置矩陣＋間歇性**

| 裝置 | BLE stack | 結果 |
|---|---|---|
| Google Pixel Tablet | stock Android | ✅ 正常 |
| Amazon Fire Max | Fire OS | ❌ 故障 |
| Lenovo Duet | ChromeOS / ARC | ⚠️ 時好時壞 |

Same binary, different outcomes → not a build, R8, or protocol problem.
Intermittent on the same device → a **race**, not a static misconfiguration.
This demoted 成因 1 (would be deterministic) and 成因 2 (would be persistent),
and promoted two new one-line candidates:

- **成因 A** — `discoverServices()` called the instant STATE_CONNECTED arrives,
  with zero delay. Known to return an empty service list on slow stacks.
- **成因 B** — `connectGatt()` without `TRANSPORT_LE` (defaults to
  `TRANSPORT_AUTO`); the pencil is already HID-linked, so the stack might attach
  over the wrong transport.

**T-07 根因確認 (2026-08-31 12:04)：`status=0 count=0`** ✅ 已結案

Reproduced on the Duet by: reboot (worked fine) → unpair **while connected** →
re-pair → fault appears. User notes the fault historically showed up on **first
pairing**, which fits.

```
[12:03:39] Device disconnected: CF:9E:8E:C7:AD:32
[12:03:40] Connecting -> eiP USI2.0 Ultra [CF:9E:8E:C7:AD:32] (bonded)
[12:03:50] GATT Error: status=257
[12:03:50] Connecting -> eiP USI2.0 Ultra [CF:9E:8E:C7:AD:32] (not bonded)
[12:04:02] Connect timeout, retrying: CF:9E:8E:C7:AD:32
[12:04:05] Connecting -> eiP USI2.0 Ultra [CF:9E:8E:C7:AD:32] (bonded)
[12:04:07] Device connected: CF:9E:8E:C7:AD:32
[12:04:07] Services discovered: status=0 count=0
[12:04:07]   UUIDs: (none)
[12:04:07] X ffe0 NOT FOUND - every command will be silently dropped
[12:04:07] X NOTIFY ABORT - ffe0/ffe3 not found
[12:04:08] X SEND ABORT - service ffe0 not found: 55 AA F1 01 00 17
```

- `status=0 count=0` — discovery reports **GATT_SUCCESS with an empty service
  list**, not even the mandatory 1800/1801 GAP/GATT services. That is the
  signature of discovery completing before the stack populated anything.
- `Device connected` and `Services discovered` share the **same second**.
- **Bond state churns across attempts**: `(bonded)` → `(not bonded)` →
  `(bonded)`. The app calls `discoverServices()` while bonding is still
  settling. `status=257` = `BluetoothGatt.GATT_FAILURE` (0x101).
- ✅ **成因 A 確認.**
- ✅ **成因 B 排除** — wrong transport would yield the *wrong* services
  (1812 etc.), not *zero*. `TRANSPORT_LE` stays as optional hygiene.
- ✅ **成因 1 排除** — the log shows the correct device, `eiP USI2.0 Ultra`.
- ✅ **讀法 B 排除** — writes never leave the app, so Factory Reset is *not*
  silently wiping user settings.

**兩個缺陷，要一起修**
1. **競態** — `discoverServices()` fires the instant STATE_CONNECTED arrives,
   including while bonding is still settling.
2. **無法復原** — once discovery returns empty, READY is declared anyway and
   nothing ever re-discovers. A transient race becomes a permanent dead session.
   This is why a reboot "fixes" it.

**提案（待核准）**
- (a) delay ~600 ms after STATE_CONNECTED before `discoverServices()`; ideally
  also wait out `BOND_BONDING`.
- (b) do **not** declare READY unless ffe0 + ffe2 + ffe3 all resolve. On failure,
  re-run `discoverServices()` a couple of times (~800 ms apart) before giving up.
- (c) move `connectTimeoutJob?.cancel()` so it only fires on a genuinely usable
  connection — then a discovery that never yields ffe0 is torn down by the
  existing 12 s watchdog and auto-connect retries, instead of sitting in
  fake-READY forever.
- (d) optional: `TRANSPORT_LE` on `connectGatt()` — hygiene, not the cause.
- (e) optional: `gatt.refresh()` via reflection. ⚠️ Hidden API, restricted on
  newer Android — best-effort only.

⚠️ (c) is a **real behaviour change**: a connection that discovers services but
lacks ffe0 is dropped rather than shown as connected. Regression-test on Pixel.

## BLE 回呼雙簽章 knowhow ⭐

**這是本專案踩過最貴的一個坑，務必先讀。**

`BluetoothGattCallback` 的多個回呼在 **Android 13 (API 33)** 有了新簽章，舊簽章
被標為 deprecated 但**沒有被移除**。框架依裝置的 API 等級決定呼叫哪一個：

| 裝置 API | 框架呼叫 |
|---|---|
| ≥ 33 | 新簽章（帶 `value: ByteArray`） |
| ≤ 32 | **舊簽章**（值要自己從 `characteristic.value` 讀） |

**父類別兩者都是空實作，彼此不會互相轉呼叫。** 只覆寫新簽章，在 API 32 以下
的裝置上就是「每一則通知都被靜默丟棄」——而且**沒有任何錯誤**：連得上、服務找
得到、寫得出去，就是永遠收不到東西。

受影響的回呼（本專案至少用到前兩組）：
- `onCharacteristicChanged(gatt, char)` / `(gatt, char, value)`
- `onCharacteristicRead(gatt, char, status)` / `(gatt, char, value, status)`
- `onDescriptorRead` 也有同樣的雙簽章

### 正確寫法：兩個都覆寫

```kotlin
// API 33+
override fun onCharacteristicChanged(gatt: BluetoothGatt, ch: BluetoothGattCharacteristic, value: ByteArray) {
    processReceivedData(value)
}

// API 32 以下 — 少了這個，舊裝置全部收不到
@Suppress("DEPRECATION")
override fun onCharacteristicChanged(gatt: BluetoothGatt, ch: BluetoothGattCharacteristic) {
    processReceivedData(ch.value ?: return)
}
```

框架只會呼叫其中一個，不會重複處理。

### 為什麼這個坑特別難發現
- `minSdk = 24`，所以 **API 24–32 的所有裝置全中**（Fire 平板、舊 Android 平板）。
- 開發機通常是新機（Pixel API 34），永遠測不出來。
- 失敗的樣子跟「裝置沒回應」一模一樣，會誤導人去查協定、去查連線。
- 編譯完全不會警告——沒覆寫舊簽章不是錯誤。

### 診斷技巧：用 dexdump 比對兩顆 APK 的回呼集合

不用原始碼也能查，對「以前正常、現在壞了」特別有效：

```bash
BT=~/Library/Android/sdk/build-tools/36.1.0
unzip -o -q app.apk 'classes*.dex' -d out/
for d in out/classes*.dex; do
  $BT/dexdump -d "$d" | grep -oE "gattCallback\\\$1\\.on[A-Za-z]+:\\([^)]*\\)V"
done | sort -u
```

拿正常版和故障版各跑一次，`diff` 一下就知道少了什麼。

## 已知地雷 ⚠️

- **`X SCAN ERROR - callback is null` 在 Fire Max 與 Duet 開機時都會出現**，
  發生在 ViewModel init 後的第一輪掃描。不影響後續運作（裝置照樣找得到），
  但兩台非原生堆疊都會，值得查。原生 Android 未見。
- **`BluetoothGattCallback` 的舊/新雙簽章必須都覆寫。** 只寫新的，API 32 以下
  的裝置收不到任何通知，且毫無錯誤徵兆。見上方 knowhow 章節。這是 1.0.2 之後
  的回歸，也是 Fire Max「送得出去、收不回來」的成因。
- **電量顯示自 1.0.5 起就是死的。** `_batteryLevel` 唯一被賦值的地方是
  `resetState()` 裡的 `= null`；程式中沒有任何 `readCharacteristic()` 呼叫，
  `onCharacteristicRead` 兩個簽章也都遺失了。但 UI 仍保留
  `if (batteryLevel != null) Text("🔋 …")`（DebugScreen.kt:253）——那行永遠
  不會執行。要修得先反組譯 1.0.2 確認它讀的是哪個 characteristic。
- **`hasReceivedInitialStatus`** guards against late-arriving initial query
  responses overwriting user edits. Preserve when touching
  `processReceivedData()` or any setter.
- **One GATT connection at a time.** Switching pencils = disconnect A → 600 ms
  settle → connect B. `manualSwitching` pauses auto-connect during this.
- **`onCleared()` must close GATT.** Leaking the connection leaves the pencil
  held by a dead session and the next launch cannot connect.
- **12 s connect watchdog** exists to break the "stuck in CONNECTING →
  auto-connect thinks it is still trying → never retries" deadlock. Do not
  remove.
- **`isKeyboard` / `DeviceType` are dead code.** Declared in BleData.kt, never
  referenced. Device filtering is name-only (`contains "eip"`, excluding
  "magnetix"), so an eiP keyboard is indistinguishable from a pencil to the
  auto-connect loop. Relevant to T-07 成因 1 and to T-02.
- **`TopHeader` hardcodes the title `"USI 2.0 Ultra"`** (DebugScreen.kt:203).
  The screen never shows which device is actually connected — only the dropdown
  does. Do not trust the header when diagnosing connection problems.
- **Never call `discoverServices()` immediately on STATE_CONNECTED.** Confirmed
  in the field to return `status=0 count=0` on ChromeOS/ARC while bonding is
  still settling. See T-07 根因確認.
- **READY does not mean usable.** `onServicesDiscovered()` declares READY
  without checking that the ffe0 service and its characteristics resolved. A
  connection can sit in READY with every command silently discarded. See T-07.
- **Do not re-add `ACCESS_FINE_LOCATION` without the `hardware.location*`
  overrides.** Declaring the permission implies `required=true` GPS hardware,
  which makes Play mark Fire tablets and most Chromebooks incompatible.
- **`isNearby` is set `true` for all bonded pencils**, not just ones actually
  in range — deliberate, because on ChromeOS a connected pencil often stops
  advertising and is invisible to both scan and `getConnectedDevices(GATT)`.
  Relevant to T-02: it means `isNearby` is not a proximity signal.
- **Sent packets are never logged.** `LogType.SENT` is declared and coloured in
  the UI but **never produced** — `sendPencilCommand()` calls no `addLog()`.
  `sendCommand()` also discards the `writeCharacteristic` return value. So the
  Communication Log shows only what came back, never what went out or whether it
  went out. This blocks diagnosis of T-07. (CLAUDE.md claims all comms are
  mirrored to the log — that is currently inaccurate for the send direction.)
- **R class is `com.eip.device.R`**, never `com.example.eip.R` — namespace and
  source package differ.
- **Release signing reads `local.properties`**, which currently holds only
  `sdk.dir`. CLI `bundleRelease`/`assembleRelease` produce unsigned artifacts.
  Working builds come from Android Studio's Generate Signed Bundle wizard
  (alias `upload`, output lands in `app/release/`).
